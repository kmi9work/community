# Техническое описание системы

Человеческое описание системы — файл `ОПИСАНИЕ.md` (источник истины: цели,
сущности, шаги пользователей, административный интерфейс, права). Здесь — как
система устроена технически: состав, модель данных, кнопки, алгоритмы работы,
ограничения мессенджеров и деплой.

Человеческое описание относится к любому сообществу; специфика сообщества
«Кузница» — в `personal_docs/`.

## Состав системы

1. **Бот-бэкенд** — Python (Django / FastAPI). Ведёт диалог с участником, считает
   сценарии, собирает форму, готовит рассылки, отдаёт API админке.
2. **Адаптер Телеграм** — Telegram Bot API, обновления по webhook.
3. **Адаптер MAX** — MAX Bot API (`https://platform-api2.max.ru`), обновления
   по webhook.
4. **CRM и админка** — фронт React (PWA-режим), база — PostgreSQL. Доступ только
   у администраторов, вход по логину и паролю.
5. **Воркер рассылки** — отдельный процесс, разбирает очередь «Доставка
   рассылки» и отправляет сообщения через адаптеры.
6. **Планировщик** — периодический запуск напоминаний и системных рассылок
   (перенос, отмена).
7. **nginx** — публичный фронт домена `kmi9site.ru`, TLS от Let's Encrypt,
   проксирование на бэкенд по `127.0.0.1`.

Участники в CRM не заходят и API админки не вызывают: всё, что им доступно, —
сообщения и кнопки бота. Учётные записи есть только у администраторов; ролей
внутри CRM нет, все администраторы видят и могут всё.

## Архитектура

```
Телеграм ─┐
          ├─→ webhook → бот-бэкенд → PostgreSQL (сущности CRM)
MAX ──────┘        (сценарии, форма)
                              ↓
                   очередь → воркер → адаптеры → Телеграм / MAX

Админка (React, PWA) → API бэкенда → PostgreSQL
Планировщик → напоминания и системные рассылки → очередь
```

**Один бэкенд, два мессенджера.** Логика сценариев, формы и рассылок не зависит
от мессенджера. Адаптер приводит входящее событие к одному внутреннему виду
(текст, нажатие кнопки, контакт, старт) и умеет три исходящих операции:
отправить сообщение, отправить картинку с подписью, отредактировать сообщение.
Различия мессенджеров — в `docs/form/telegram.md` и `docs/form/max.md`.

**Состояние — в базе, не в памяти процесса.** Текущий шаг регистрации, прохождение
опроса и очередь доставки лежат в PostgreSQL. Перезапуск или деплой бота не теряет
начатый диалог; второй экземпляр бэкенда не ломает прохождение.

**Входящее событие.** Адаптер принимает webhook, проверяет подпись и отсекает
повторы (Телеграм — по `update_id`, MAX — по `timestamp` и `callback_id`), затем
передаёт событие в диспетчер. Диспетчер по состоянию диалога выбирает обработчик:
регистрация, меню, шаг формы, ввод текста. Тяжёлая работа (запись в CRM, отправка
следующего шага) выполняется асинхронно: webhook отвечает мессенджеру сразу, иначе
мессенджер повторит доставку события.

**Исходящее сообщение.** Любая отправка участнику идёт через сервис отправки: он
подставляет лимиты адаптера, делает паузу между сообщениями, при ошибке повторяет
и пишет в «Доставку рассылки» идентификатор сообщения или ответ мессенджера.

## Модель данных

Объекты CRM и их назначение. Полный перечень полей с признаком обязательности —
в `ОПИСАНИЕ.md`, раздел «Сущности в CRM».

| Объект | Назначение | Ключевые правила |
| --- | --- | --- |
| Участник | карточка человека | идентификаторы мессенджеров уникальны; телефоны — нет |
| Документ о согласии | редакция текста согласия | «Действует» — одна редакция |
| Согласие | факт согласия на редакцию | новая редакция — новая запись |
| Уровень участия в сообществе | уровень сообщества | `identifier`, типы мероприятий |
| Тип деятельности | вид деятельности на уровне | `identifier` |
| Тип мероприятия | направление (игры, лекции, …) | `identifier`, уровень, подписчики |
| Мероприятие | событие | статус: запланировано / перенесено / отменено / проведено |
| Участие в мероприятии | связка «участник — мероприятие» | статус записи, роль, явка |
| Участие организатора | связка «организатор — мероприятие» | ролей несколько |
| Роль на игре | справочник ролей | вид: участник / организатор; «Активна» |
| Подписка на тип мероприятия | согласие получать анонсы | «Подписан» + дата изменения |
| Интерес участника | выбранные уровни и деятельности | подписку не снимает |
| Вопрос | вопрос анкеты или опроса | тип ответа, звёздочка, порядок |
| Вариант ответа | вариант для вопроса-выбора | порядок, «Активен» |
| Опросник | анкета записи или опрос | назначение, «Активен» |
| Прохождение опроса | один заход в форму | статус, текущий вопрос, канал |
| Ответ | ответ на вопрос | одна строка — один ответ |
| Отказ от опроса | отказ от опросника или всех | пустой опросник — отказ от всех |
| Напоминание | срок напоминания о мероприятии | «За сколько до начала», «Отправлено» |
| Рассылка | задание на отправку | вид, способ выбора получателей, статус |
| Доставка рассылки | строка «участник + канал» | статус, попытка, ошибка |

**Связи.**

1. Уровень → типы мероприятий и типы деятельности. Подписка ставится по типам
   уровня.
2. Интерес участника (уровень + деятельность) → подписка на типы мероприятий
   уровня. Снятие интереса подписку не меняет: подпиской управляет кнопка
   «Отписаться от уведомлений ленты».
3. Вопрос → варианты ответа. Вопрос → прохождение → ответ. Ответ всегда привязан
   к прохождению; повторный ответ на вопрос со звёздочкой добавляет строку, а не
   перезаписывает прежнюю.
4. Рассылка → доставки. Строки доставки создаются на каждую пару «участник +
   канал» в момент запуска.
5. Мероприятие → участия, участия организаторов, напоминания, рассылки.

**Общие правила.**

1. `identifier` после создания не меняется; переименование — только через поле
   «Название».
2. Справочные записи не удаляются: выведенная из обращения роль или тип
   переводится в «Активна = нет».
3. Роль на мероприятии хранится ссылкой на справочник: переименование меняет
   название везде, включая прошедшие мероприятия.
4. Один человек — одна карточка: идентификатор второго мессенджера
   привязывается к существующей карточке. Совпадение контактных телефонов
   карточки не склеивает.
5. При отписке от ботов в обоих мессенджерах карточка переводится в «удалён»:
   персональные данные и идентификаторы стираются, дата удаления сохраняется.

## Регистрация участника (Шаг 0)

Состояния шага: `нет карточки` → `имя` → `телефон мессенджера` → `карточка` →
`контактный телефон` → `согласие` → `зарегистрирован`. Шаг хранится в базе,
поэтому повторный `/start` продолжает диалог с текущего шага, а не начинает заново.

1. **Приветствие.** Новый пользователь получает `01-start.md`; карточка ещё не
   создана.
2. **Имя и фамилия.** Если мессенджер отдал имя в профиле — `02-name-confirm.md`
   с кнопками «Да» (`reg:name_yes`) и «Ввести заново» (`reg:name_no`). Если имени
   нет — бот сразу просит написать имя и фамилию одним сообщением, кнопок нет.
   Принимается только текст; ответ разбирается на имя и фамилию.
3. **Телефон мессенджера.** `03-phone-request.md` с кнопкой запроса контакта.
   Номер, набранный руками, на этом шаге не принимается — бот повторяет просьбу.
   Без доступа к телефону регистрация не продолжается: `04-phone-required.md`
   отправляется один раз, диалог остаётся на шаге.
4. **Поиск карточки.** По номеру телефона мессенджера ищется карточка участника.
   Если номер уже есть у карточки из другого мессенджера — `05-known-card.md` с
   кнопками «Это я» (`reg:card_yes`) и «Нет, я новый» (`reg:card_no`). «Это я» —
   идентификатор мессенджера привязывается к найденной карточке; «Нет, я новый» —
   создаётся отдельная карточка, совпадение телефонов карточки не склеивает.
5. **Контактный телефон.** `06-contact-phone-offer.md`: «Указанный в
   `{{messenger}}` телефон `{{phone}}` можно использовать как Ваш контактный?»
   Кнопки «Да» (`reg:contact_yes`) и «Другой номер» (`reg:contact_no`). «Другой
   номер» — `07-contact-phone-ask.md`, принимается текст с номером; если номера в
   тексте нет, бот просит написать ещё раз. Без контактного телефона регистрация
   не завершается (`08-contact-phone-required.md`).
6. **Согласие на обработку ПД.** `09-consent.md` со ссылкой действующей редакции
   документа (справочник «Документ о согласии», адрес-образец — `personal_docs/law.md`).
   Кнопки «Согласен» (`reg:consent_yes`) и «Не согласен» (`reg:consent_no`).
   Согласие сохраняется отдельной записью: редакция, канал, дата и время; признак
   в карточке — «да».
7. **Отказ.** «Не согласен» — `10-consent-declined.md`, регистрация не создаётся,
   собранные до этого шага данные в карточке не сохраняются.
8. **Завершение.** Карточка создана или привязана к существующей,
   `11-registered.md` с постоянным меню и строкой подписок. Подписки ставятся по
   всем типам мероприятий уровня `new` («Подписан = да»).
9. **Удаление.** Отписка от ботов в обоих мессенджерах переводит карточку в
   «удалён»: персональные данные и идентификаторы стираются, дата удаления
   сохраняется.

Постоянное меню участника: «Мероприятия», «О сообществе», «Мои данные»,
«Написать организатору». Меню приходит текстом кнопки; во время формы оно скрыто,
чтобы участник не сбил прохождение.

## Сценарий №1. Запись на мероприятие

**Вход в сценарий — два.**

1. Меню «Мероприятия» → `20-events-type.md`: кнопки по одной на каждый активный
   тип мероприятия (`ev:type:<identifier>`) и «Все» (`ev:all`) последней.
   Дальше бот отправляет предстоящие мероприятия выбранного типа (или всех типов):
   афишу с подписью и кнопкой «Записаться».
2. Анонс от администратора: `22-event-announcement.md` с кнопками «Записаться»
   (`ev:join:<event_id>`) и «Отписаться: (тип)» (`ev:unsub:<type_id>`) в том же
   сообщении, что и афиша.

**Выборка предстоящих.** Статус «запланировано» или «перенесено», дата не раньше
текущей; сортировка по дате и времени. Если подходящих нет — `21-events-none.md`.

**Подпись анонса.** Название, дата и время, адрес. Если время не указано, строка
выводится без запятой и пустого места; если адрес не указан, строка убирается
целиком. Короткое описание добавляется абзацем, только если вся подпись остаётся
в лимите подписи к фото; длинное описание уходит отдельным сообщением
(`23-event-description.md`) с теми же кнопками.

**Нажатие «Записаться»** (`ev:join:<event_id>`):

1. Ищется участие участника в этом мероприятии. Если есть со статусом
   «записан» — `25-event-already-registered.md`, вторая запись не создаётся.
2. Создаётся прохождение опроса по анкете записи: статус «начат»,
   мероприятие = текущее, канал = мессенджер, начат = сейчас.
3. Отбираются вопросы анкеты: активные, по порядковому номеру. Вопрос со
   звёздочкой («Спрашивать при каждой записи») задаётся всегда; остальные
   пропускаются, если у участника уже есть ответ на этот вопрос — проверка
   глобальная, по объекту «Ответ», в любом опроснике и на любом мероприятии.
4. Вопросов не осталось — форма не отправляется, сразу создаётся запись и
   приходит `24-event-registered.md`.
5. Иначе форма идёт по правилам раздела «Форма в боте». Каждый ответ пишется в
   объект «Ответ» с привязкой к прохождению и мероприятию.
6. Завершение формы: создаётся «Участие в мероприятии» со статусом «записан»,
   роль участника пустая до выдачи роли в админке, дата записи = сейчас.
   Ответы остаются привязанными к мероприятию.
7. Отказ от формы (`x:<прохождение>`) — прохождение в статус «отказ», запись не
   создаётся, `30-form-declined.md`.

**Отписка** (`ev:unsub:<type_id>`): «Подписка на тип мероприятия» получает
«Подписан = нет» и дату изменения, приходит `26-unsubscribed.md`. Анонсы этого
типа больше не приходят, остальные подписки не меняются.

**Идемпотентность.** Повторное нажатие «Записаться» не создаёт вторую запись и
второе прохождение: участие и активное прохождение ищутся по паре «участник +
мероприятие». Дубль события от мессенджера отсекается на входе.

## Форма в боте

Форма собирается нативными сообщениями и inline-кнопками: один вопрос — одно
сообщение бота с кнопками (выбор) или без них (открытый ответ). Мини-приложения
Телеграм и MAX не используются: один бэкенд на два мессенджера, одинаковое
поведение, не нужен хостинг фронта и два разных моста.

**Шаг формы.** Бот отправляет «Вопрос `{{n}}` из `{{m}}`», текст вопроса и
клавиатуру. Ответ приходит либо нажатием кнопки (callback), либо текстовым
сообщением (открытый вопрос). Бэкенд пишет «Ответ», снимает клавиатуру правкой
сообщения и переходит к следующему вопросу.

**Правила.**

1. Порядок вопросов — по «Порядковому номеру», только «Активные».
2. Вопросы со звёздочкой задаются при каждой записи; остальные — только если
   ответа на вопрос у участника ещё нет.
3. Обязательный вопрос пропустить нельзя — кнопки «Пропустить» в нём нет. В
   необязательном она есть (`s:<номер вопроса>`).
4. Выбор одного варианта: нажатие сразу считается ответом, кнопки гасятся,
   выбранный вариант остаётся в тексте сообщения.
5. Выбор нескольких: кнопки-переключатели (`m:<вопрос>:<вариант>:<бит>`), ответ
   отправляется кнопкой «Готово» (`g:<номер вопроса>`). Лимит «Максимум выбранных
   вариантов» проверяет бот; при превышении лишний вариант снимается, остальные
   отметки сохраняются, отдельным сообщением приходит `28-form-multi-limit.md`.
6. Открытый ответ: принимается только текст, команды и нажатия старых кнопок
   игнорируются с подсказкой `29-form-open-answer.md`. Текст длиннее лимита
   мессенджера не обрезается: `91-text-too-long.md`, шаг остаётся прежним.
7. Идемпотентность: повторное нажатие на уже отвеченный вопрос не создаёт второй
   ответ (кроме вопросов со звёздочкой, где повторный ответ — норма).
8. Сообщение с вопросом редактируется, а не дублируется: одно сообщение — один
   вопрос. Отдельное сообщение отправляется только при ошибке или предупреждении.
9. «Отказаться от опроса» (`x:<прохождение>`) доступна в первом сообщении формы
   и на каждом шаге: прохождение получает статус «отказ», отказ пишется в «Отказ
   от опроса»; при записи на мероприятие участие не создаётся.
10. Возобновление: прохождение в статусе «начат» живёт до завершения или отказа.
    По `/start` бот предлагает продолжить с «Текущего вопроса».
11. Текст ответа ограничен лимитом мессенджера: 4096 символов в Телеграм,
    4000 — в MAX. Слишком длинный ответ бот не обрезает.
12. Ошибки сети: повтор с задержкой; при ответе «слишком часто» — пауза из ответа
    мессенджера. Каждая отправка логируется (канал, идентификатор сообщения,
    идентификатор callback), дубль сообщения участнику недопустим.

**Коды кнопок формы.** В кнопку кладётся короткий латинский код, расшифровка —
по данным CRM, поэтому переименование варианта не ломает старые кнопки:

```
q:<вопрос>:<вариант>          выбор одного варианта
m:<вопрос>:<вариант>:<бит>    переключатель для выбора нескольких
g:<вопрос>                    «Готово»
s:<вопрос>                    «Пропустить»
x:<прохождение>               «Отказаться»
```

Ограничение Телеграма: `callback_data` — 1–64 **байта**, поэтому кириллица в
кнопку не помещается. В MAX `payload` — до 1024 символов, но коды те же.

**Различия мессенджеров** (подробно — `docs/form/telegram.md`,
`docs/form/max.md`):

1. Телеграм: `sendMessage` / `sendPhoto` / `editMessageText` /
   `editMessageReplyMarkup` / `answerCallbackQuery`; `answerCallbackQuery`
   вызывается на каждое нажатие; правка сообщения старше 48 часов запрещена —
   тогда отправляется новое сообщение.
2. MAX: `POST /messages`, `PUT /messages?message_id=`, `POST /answers?callback_id=`;
   клавиатура — вложение сообщения, пустой массив вложений убирает клавиатуру;
   токен только в заголовке `Authorization`.
3. В Телеграм — не больше трёх кнопок в ряду; в MAX — до 7 в ряду (до 3 для
   ссылок и открытия приложения).
4. Название кнопки — до 20 символов в Телеграм и по вёрстке 5–20 в MAX; длинный
   вариант сокращается в кнопке, полный текст показывается во всплывающем
   уведомлении.

## Сценарий №2. Админ отправляет участникам опросник

1. Администратор открывает карточку опросника и нажимает «Разослать опрос».
2. Выбирает получателей: выбранные участники или все, подписанные на выбранные
   уровни (уровней можно выбрать несколько). Участники с отказом от этого
   опросника или с признаком «Отказ от всех опросов» в получатели не попадают.
3. Предпросмотр: текст сообщения `40-survey-invite.md`, число получателей и их
   список. «Отправить себе» — тестовая отправка только автору, в статистику
   обычной рассылки не попадает.
4. Запуск создаёт «Рассылка» вида «опрос» и строки «Доставка рассылки»; дальше
   работает общая очередь раздела «Рассылки и доставка».
5. Участник получает приглашение с кнопками «Пройти опрос» (`sv:take:<опросник>`),
   «Отказаться» (`sv:decline:<опросник>`) и «Отказаться от всех» (`sv:decline_all`).
6. «Пройти опрос» создаёт прохождение по опроснику (мероприятие пустое) и ведёт
   форму по правилам раздела «Форма в боте» — с теми же вопросами-фильтрами:
   отвеченные ранее пропускаются, вопросы со звёздочкой задаются снова.
7. «Отказаться» — `41-survey-declined.md`: отказ пишется в «Отказ от опроса» с
   указанием опросника, прохождение получает статус «отказ».
8. «Отказаться от всех» — `42-surveys-all-declined.md`: отказ без опросника плюс
   флаг «Отказ от всех опросов» в карточке участника. Анонсы мероприятий
   продолжают приходить.
9. Прогресс сохраняется: участник может отвечать по одному вопросу и вернуться
   позже — в «Мои данные» → «Опросы» видны незавершённые прохождения с текущим
   вопросом.

## Сценарий №3. Подписка на мероприятия

1. Кнопка «О сообществе» → `50-about.md`: текст из `personal_docs/description.md`,
   уровни и типы деятельности из `personal_docs/levels.md`, кнопки «Выбрать
   интересы» (`int:start`) и «Мероприятия».
2. Если текст не помещается в лимит мессенджера, уровни отправляются отдельными
   сообщениями — по одному на уровень, в порядке списка.
3. Выбор интересов: уровни (`int:level:<id>`) и в каждом уровне типы деятельности
   (`int:activity:<id>`); отметок может быть несколько. Сохранение — `int:save`,
   подтверждение — `51-interests-saved.md`.
4. Сохранение пишет «Интерес участника» (участник + уровень + деятельность, дата
   изменения) и ставит «Подписан = да» по всем типам мероприятий выбранных
   уровней.
5. Снятие интереса подписку не меняет: подпиской управляет кнопка «Отписаться от
   уведомлений ленты». Действует последнее действие участника.

`me:data` без изменений.

## Сценарий №5. Напоминания

1. В карточке мероприятия на вкладке «Напоминания» администратор задаёт строки:
   «За сколько до начала» (часы), текст (пусто — текст сообщества по умолчанию),
   «Активно».
2. Планировщик периодически сверяет строки со временем начала мероприятия. Для
   каждой активной строки, чей срок наступил и которая ещё не отправлена,
   создаётся «Рассылка» вида «напоминание» (автор — система) со способом выбора
   получателей «записанные на мероприятие».
3. Получатели — только участия в статусе «записан». Отменившим запись
   напоминание не приходит.
4. Текст — `70-reminder.md`: название, дата и время, адрес; кнопки «Написать
   организатору», «Мои данные».
5. Отправка видна в карточке мероприятия и в «Доставке рассылки»: кому ушло, кому
   не дошло и почему. В строке напоминания фиксируются дата и время отправки.
6. При переносе или отмене мероприятия напоминания о прежних дате и времени не
   отправляются; после переноса расчёт идёт от новых даты и времени.

## Сценарий №6. Перенос/отмена мероприятия

**Перенос.** Администратор меняет дату, время или адрес в карточке мероприятия.
Действие требует подтверждения и причины:

1. прежние дата и время сохраняются в полях «Прежняя дата и время»;
2. причина пишется в «Причина переноса или отмены»;
3. статус мероприятия — «перенесено»;
4. создаётся системная «Рассылка» вида «изменение мероприятия» для записавшихся,
   текст — `80-event-moved.md` («Было / Стало», новый адрес);
5. записи, роли и ответы анкеты сохраняются, напоминания считаются от новых даты
   и времени.

**Отмена.** Статус «отменено» и обязательная причина в том же поле. Создаётся
рассылка вида «изменение мероприятия» с текстом `81-event-cancelled.md`
(причина, запись сохраняется). Напоминания не отправляются, записи остаются в CRM.

В обоих случаях уже отправленные сообщения не отзываются, а рассылка видна в
общем списке рассылок и использует ту же очередь и тот же учёт доставки.

## Рассылки и доставка

**Статусы рассылки:** `черновик` → `в очереди` → `отправляется` → `завершена`;
из `черновика` и `в очереди` возможна `отменена` с причиной.

Алгоритм запуска:

1. Администратор задаёт вид (анонс мероприятия / опрос / текст), тему, объект
   (мероприятие или опросник), текст, способ выбора получателей и список.
2. Предпросмотр считает получателей и показывает список; «Отправить себе» —
   тестовая отправка только автору, в статистику обычной рассылки не попадает.
3. После подтверждения адресаты фиксируются: на каждую пару «участник + канал»
   создаётся строка «Доставка рассылки» со статусом «в очереди», попытка = 1.
   Число получателей пишется в рассылку.
4. Воркер берёт строки очереди, отправляет через адаптер канала, пишет
   идентификатор сообщения и время, переводит строку в «отправлено» или «ошибка»
   с ответом мессенджера. Рассылка получает «отправляется», затем «завершена».
5. Прогресс, доставлено и ошибки видны в карточке рассылки; на вкладке
   «Доставка» — строки с номером попытки и ответом мессенджера.
6. «Повторить ошибки» возвращает строки со статусом «ошибка» в очередь, увеличивая
   номер попытки. При ответе мессенджера «слишком часто» воркер ждёт время из
   ответа, а не повторяет сразу.
7. Отмена начатой рассылки останавливает неотправленные строки; уже доставленные
   сообщения не отзываются.

**Способы выбора получателей:** все активные участники; по типам мероприятий; по
уровням; выбранные участники; записанные на мероприятие.

**Системные рассылки.** Напоминания и сообщения о переносе или отмене создаёт
бот. Автор — система; виды — «напоминание» и «изменение мероприятия».

**Гарантии.** Одна строка доставки — одно сообщение: повторы не должны давать
дубль в чате участника. Ключ идемпотентности — «рассылка + участник + канал».
Строка доставки хранит номер попытки, поэтому сбой на середине очереди виден и
продолжается с места остановки.

## Административный интерфейс

Вход — логин и пароль администратора.

### Навигация

Слева — разделы:

1. **Участники**
2. **Мероприятия**
3. **Опросы**
4. **Рассылки**
5. **Справочники** — типы мероприятий, уровни участия, типы деятельности, роли
   на игре, документы о согласии.

Каждый раздел открывается списком. В списках есть поиск, фильтры, сортировка,
выбор колонок и inline-редактирование. Набор фильтров сохраняется как
представление: «Предстоящие игры», «Ошибки доставки», «Брошенные прохождения»,
«Отменили запись», «Отписались».

### Мероприятия

**Список.** Колонки: название, тип, дата и время, место, статус, записано (и
лимит мест), афиша, разослан ли анонс. Фильтры: предстоящие / прошедшие, тип,
статус. Кнопка «Добавить мероприятие».

**Новое мероприятие.** Форма с обязательными полями: название, тип, дата. После
сохранения статус — «запланировано», мероприятие сразу видно в боте в списке
предстоящих. Время, адрес, афиша, описание, лимит мест и организаторы
заполняются в карточке.

**Карточка мероприятия.** Вкладки: «Основное», «Участники», «Организаторы»,
«Напоминания», «Рассылки», «Ответы».

Кнопки на вкладке «Основное» и что они меняют:

| Кнопка | Что делает | Что меняется в CRM |
| --- | --- | --- |
| «Разослать анонс» | предпросмотр анонса | «Рассылка» вида «анонс» + доставки |
| «Перенести» | новые дата, время, адрес, причина | «Прежняя дата и время», причина, статус «перенесено», рассылка |
| «Отменить» | причина обязательна | статус «отменено», причина, системная рассылка |
| «Провести» | подтверждение | статус «проведено», уходит из предстоящих в боте |
| «Список для мастера» | печатная страница | ничего не меняет |

**Анонс.** Предпросмотр показывает сообщение с афишей, текстом, кнопками
«Записаться» и «Отписаться: (тип)», число получателей и их список. Получатели —
активные участники, подписанные на тип мероприятия. «Отправить себе» — тестовая
отправка автору; «Отправить» — создание рассылки и постановка в очередь. Начатую
рассылку можно отменить, доставленные сообщения не отзываются.

**Афиша.** JPEG или PNG, 1080 × 1350, до 5 МБ. При сохранении проверяются
формат, размер в пикселях и вес; неподходящий файл не сохраняется, причина
показывается рядом с полем. Требования к макету — `docs/afisha.md`. Бот отправляет
картинку как есть, не обрезая и не накладывая текст.

**Участники.** Список записавшихся: имя и фамилия, контактный телефон, статус
записи, роль участника, присутствие, дата записи, ответы на вопросы со
звёздочкой. Роль выбирается из активных ролей вида «участник». Статус записи и
присутствие меняются в списке; по просьбе участника администратор переводит
запись в «отменил запись». Участник с отменённой записью остаётся в списке.

**Организаторы.** Список организаторов мероприятия; каждому выбирается одна или
несколько ролей вида «организатор».

**Явка.** «Пришёл» / «Не пришёл» в списке участников, в том числе массово —
«Отметить всех пришедшими» и «Снять отметки». Явку можно поправить и после
проведения мероприятия.

**Список для мастера.** Печатная страница: название, дата, время, адрес и
таблица участников со статусом «записан» — имя и фамилия, контактный телефон,
роль, ответы на вопросы со звёздочкой, пустая колонка для отметки явки.

**Напоминания.** На вкладке строки «За сколько часов до начала», текст, «Активно»,
дата и время отправки. Алгоритм — «Сценарий №5».

### Опросы

**Опросники.** Список с назначением («анкета записи на мероприятие» / «опрос») и
признаком «Активен». В карточке — описание, вопросы и варианты ответов: текст,
тип ответа, обязательность, «Спрашивать при каждой записи», порядковый номер,
активность. Анкета записи одна; её начальный состав — в файлах
`personal_docs/questions/(тип мероприятия).md`, дальше вопросы правятся в админке.

**Рассылка опроса.** Кнопка «Разослать опрос» на карточке опросника; получатели —
выбранные участники или все, подписанные на выбранные уровни. Предпросмотр, число
получателей, тестовая отправка себе. Отправка создаёт рассылку вида «опрос» и
строки доставки. Отказавшиеся в получатели не попадают.

**Прохождения.** Вкладка «Прохождения» в карточке опросника и вкладка «Ответы» в
карточке мероприятия: участник, мероприятие или опросник, статус, канал, начат,
завершён, текущий вопрос. Фильтры: статус, мероприятие, опросник, мессенджер.
Карточка прохождения показывает ответы по вопросам. Незавершённые прохождения
видны по «Текущему вопросу».

**Отказы.** В карточке опросника и в карточке участника видны отказы от
конкретного опросника и от всех опросов.

**Выгрузка в Excel.** Кнопка «Выгрузить в Excel» на списке прохождений и на
вкладке «Ответы» — см. раздел «Выгрузка ответов в Excel».

### Участники

**Список.** Колонки: имя и фамилия, телефон из мессенджера, контактный телефон,
мессенджеры, статус, уровни, число записей, дата регистрации. Фильтры: активен /
удалён, мессенджер, уровень, тип мероприятия, отказ от опросов. Поиск — по имени,
фамилии и телефону.

**Карточка.** Вкладки: «Данные», «Согласия», «Подписки», «Интересы», «Записи»,
«Опросы», «Отказы».

| Вкладка | Содержимое и действия |
| --- | --- |
| «Данные» | имя, фамилия, телефоны, идентификаторы, дата регистрации, статус; правка имени, фамилии и телефона |
| «Согласия» | редакция, канал, дата, статус; кнопка «Отозвать согласие» |
| «Подписки» | типы мероприятий и признак «Подписан»; включение и выключение |
| «Интересы» | уровни и типы деятельности, выбранные участником |
| «Записи» | мероприятия со статусом записи и ролью |
| «Опросы» | прохождения со статусом и текущим вопросом |
| «Отказы» | отказ от всех опросов и отказы по опросникам |

«Отозвать согласие» переводит последнюю запись в «отозвано» и ставит в карточке
«Согласие — нет». При отписке от ботов в обоих мессенджерах карточка
автоматически переводится в «удалён».

### Рассылки

**Список.** Колонки: вид, тема, статус, автор, получателей, доставлено, ошибок,
создана, завершена. Фильтры: вид, статус, период, тестовая.

**Создание.** Кнопка «Новая рассылка»: вид, тема, мероприятие или опросник, текст,
способ выбора получателей и соответствующий список. Перед запуском — предпросмотр,
число получателей и список; «Отправить себе» — только автору.

**Запуск и контроль.** После подтверждения получатели фиксируются, создаются
строки «Доставка рассылки» по каждой паре «участник + канал», статус меняется на
«в очереди», затем «отправляется» и «завершена». В карточке — прогресс,
доставлено, ошибки, причина отмены. На вкладке «Доставка» — статус, номер попытки
и ответ мессенджера; фильтр «ошибка» и кнопка «Повторить ошибки». Начатую рассылку
можно отменить, доставленные сообщения не отзываются.

### Справочники

1. **Типы мероприятий** — название, identifier, уровень, подписчики.
2. **Уровни участия** — название, identifier, типы мероприятий и типы деятельности.
3. **Типы деятельности** — название, identifier.
4. **Роли на игре** — название, identifier, вид (участник / организатор),
   порядковый номер, активность.
5. **Документы о согласии** — название, версия, ссылка, дата публикации,
   признак «Действует».

В каждом справочнике есть добавление записи и правка полей в списке или в
карточке. Правила: `identifier` после создания не меняется; выведенная из
обращения роль переводится в «Активна = нет»; действующая редакция документа о
согласии одна, новая редакция добавляется отдельной записью, прежние согласия не
перезаписываются.

### Контроль

Представления, которые показывают проблемы:

1. «Отменили запись» — участники с отменённой записью.
2. «Брошенные прохождения» — прохождения со статусом «начат».
3. «Ошибки доставки» — доставки со статусом «ошибка».
4. «Отписались» — участники с признаком «Подписан = нет» по типу мероприятия.

### Права

Доступ к CRM есть только у администраторов; ролей внутри CRM нет. Персональные
данные участников, ответы и выгрузки доступны только в CRM. Список для мастера
содержит контактные телефоны и передаётся только организаторам этого мероприятия.
Каждая рассылка и изменение мероприятия сохраняют автора и время.

## Выгрузка ответов в Excel

Кнопка «Выгрузить в Excel» на списке прохождений и на вкладке «Ответы»
мероприятия. В файл попадают прохождения, отобранные фильтром списка; по
умолчанию — завершённые.

1. Первый лист — широкий: строка — одно прохождение (участник и мероприятие или
   опросник), столбцы — вопросы опросника. Для вопроса со звёздочкой в ячейке —
   последний ответ; для «выбора нескольких» варианты через «; ».
2. Второй лист — плоский список ответов: участник, вопрос, ответ, мероприятие,
   дата. Для произвольных сводных.
3. Ответы, начинающиеся с `=`, `+`, `-` или `@`, записываются как текст, чтобы
   Excel не выполнил формулу.
4. Имя файла — `(опросник)-(дата).xlsx`.
5. Если строк слишком много, админка предупреждает и просит сузить фильтр.

## Тексты сообщений и коды кнопок

Источник текстов — `personal_docs/messages/`, одно сообщение — один файл;
правила тона и оглавление — `personal_docs/messages/README.md`. Шаблоны записаны
в HTML-разметке Телеграм; при отправке в MAX `<b>…</b>` заменяется на `**…**`.
Подстановки — `{{имя}}`; если значения нет, строка убирается целиком.

Коды кнопок регистрации и меню:

| Действие | Код |
| --- | --- |
| Подтвердить имя / ввести заново | `reg:name_yes` / `reg:name_no` |
| Нашли карточку: это я / нет | `reg:card_yes` / `reg:card_no` |
| Телефон подходит / другой номер | `reg:contact_yes` / `reg:contact_no` |
| Согласие: да / нет | `reg:consent_yes` / `reg:consent_no` |
| Тип мероприятия / все типы | `ev:type:<identifier>` / `ev:all` |
| Записаться на мероприятие | `ev:join:<event_id>` |
| Отписаться от типа | `ev:unsub:<type_id>` |
| Ответы формы | `q:` / `m:` / `g:` / `s:` / `x:` |
| Пройти / отклонить опрос | `sv:take:<survey_id>` / `sv:decline:<survey_id>` |
| Отказаться от всех опросов | `sv:decline_all` |
| Начать выбор интересов | `int:start` |
| Уровень и тип деятельности | `int:level:<id>` / `int:activity:<id>` |
| Сохранить интересы | `int:save` |
| Мои данные | `me:data` |
| Разделы «Моих данных» | `me:subs`, `me:interests`, `me:surveys`, `me:events` |
| Написать организатору | `me:org` |
| Изменить имя / телефон | `me:edit_name` / `me:edit_phone` |
| Подписка на тип | `sub:toggle:<type_id>` |

Коды латиницей и короткие: в Телеграм `callback_data` — до 64 байт, кириллица в
кнопку не помещается. Текст кнопки — до 20 символов.

## Ограничения мессенджеров

| Что | Телеграм | MAX |
| --- | --- | --- |
| Текст сообщения | 1–4096 символов | до 4000 символов |
| Подпись к картинке | до 1024 символов | до 4000 символов |
| Данные кнопки | 1–64 байта | до 1024 символов |
| Текст кнопки | до 20 символов (вёрстка) | 1–128 символов |
| Кнопок в ряду | не больше 3 | до 7 |
| Частота | ~30 сообщений/с на бота, ~1/с в чат | до 30 запросов/с на бота, 2/с в диалог |
| Обновления | webhook (long polling — локально) | только webhook |
| Адрес API | `api.telegram.org` | `platform-api2.max.ru` |

При ответе «слишком часто» бот ждёт время из ответа мессенджера. Дублирование
сообщения участнику недопустимо, поэтому каждая отправка логируется.

## Безопасность и персональные данные

1. Доступ к CRM только у администраторов: логин и пароль. Публичной регистрации и
   самостоятельного восстановления доступа у участников нет.
2. Публичный вход — только HTTPS (TLS 1.2/1.3), сертификат Let's Encrypt;
   приложение слушает `127.0.0.1`, наружу не публикуется. HTTP перенаправляется
   на HTTPS.
3. Секреты (пароль базы, ключи шифрования и подписи) генерируются на сервере при
   первом деплое, лежат в `deploy/.env` с правами 600 и в git не попадают.
4. Персональные данные, ответы и выгрузки доступны только в CRM; в боте участник
   видит только свои данные.
5. Согласие хранится записью на конкретную редакцию документа: видно, на какой
   текст, когда и в каком мессенджере человек согласился. Отзыв согласия — отдельное
   действие, прежние записи не переписываются.
6. Отписка от ботов в обоих мессенджерах удаляет персональные данные: карточка
   переводится в «удалён», идентификаторы и телефоны стираются, дата удаления
   остаётся.
7. Выгрузка в Excel экранирует значения, начинающиеся с `=`, `+`, `-`, `@`
   (защита от подстановки формул).
8. Тексты ошибок участнику не показывают технических подробностей: `90-error-retry.md`,
   детали — в логе бота.
9. Каждая рассылка и изменение мероприятия хранят автора и время.

## Наблюдаемость

Три источника фактов, и они не заменяют друг друга:

1. **Записи CRM** — что стало с данными: запись на мероприятие, статус
   прохождения, строка «Доставка рассылки» с номером попытки и ответом
   мессенджера, время действия. Основной источник отчётов: он переживает
   перезапуск, чистку журналов и переезд на другой сервер.
2. **Журналы** — что система делала в этот момент: приняла событие, выбрала
   обработчик, отправила сообщение, отказала по проверке. Нужны там, где записи
   в CRM нет или её мало.
3. **Метрики** — сколько и как быстро: поток событий по каналам, глубина очереди
   доставки, ошибки по кодам, время обработки. Показывают тенденцию, но не
   отдельную жалобу.

**Строка журнала.** Одна строка — одно событие, JSON, время в UTC. Поля: `ts`,
`level`, `service` (`bot`, `worker`, `scheduler`, `admin`), `event`,
идентификатор события (`update_id` в Телеграм, `timestamp` и `callback_id` в
MAX), участник, мероприятие, опросник, прохождение, рассылка, доставка, канал,
номер попытки, длительность и код ошибки. Недостающие поля не подставляются
пустыми: в строке только то, что относится к событию.

**Что в журнал не попадает.** Тексты ответов, телефоны, адреса, токены ботов,
пароли, содержимое согласий: в журнале идентификаторы и коды ошибок, данные — в
CRM. Техническая причина сбоя остаётся в журнале, участник получает
`90-error-retry.md` без подробностей. Правило то же, что в разделе
«Безопасность и персональные данные»: журнал не становится второй копией
персональных данных.

**Куда пишется.** Бот, воркер и планировщик пишут в stdout контейнера, nginx — в
access и error log; сбор — штатный `docker compose logs` и journald, отдельного
хранилища журналов нет. Ротация по размеру: 10 МБ на файл, 5 файлов на сервис,
старые вытесняются. Журнал не источник статистики: его потеря не меняет ни одной
записи CRM.

**Что журналируется.**

1. **Входящее событие.** Канал, тип события (сообщение, нажатие, контакт,
   `/start`), участник, результат проверки: принято, отброшено как повтор,
   отброшено по подписи или разбору.
2. **Шаг сценария.** Обработчик, шаг диалога до и после, отправленное сообщение,
   код нажатой кнопки.
3. **Отправка сообщения.** Канал, операция (сообщение, фото с подписью, правка),
   идентификатор сообщения, номер попытки, код ответа мессенджера, пауза из
   `retry_after`.
4. **Запись в CRM.** Объект, идентификатор, действие (создание, изменение,
   удаление), автор — участник, администратор или система.
5. **Рассылка.** Запуск (вид, способ выбора, сколько отобрано), готовность
   очереди, завершение с итогом «доставлено / ошибок», повтор ошибок, отмена с
   причиной.
6. **Планировщик.** Проход, найденные напоминания, созданные системные рассылки,
   пропуски с причиной (мероприятие отменено, напоминание уже отправлено).
7. **Админка.** Вход и его результат (пароль в журнал не пишется), сохранение
   карточки, запуск и отмена рассылки, смена статуса мероприятия, выгрузка в
   Excel (кто, какой опросник, сколько строк).

**Запросы к API.** Каждый запрос админки и каждый webhook оставляет строку:
метод, путь без параметров, код ответа, длительность; тело запроса и ответа не
пишется. Ошибки 4xx и 5xx годятся для сводки по путям: рост 4xx на webhook —
смена формата события у мессенджера, рост 5xx — сбой базы или кода.

**Разбор жалобы.** Идёт от идентификатора, а не от времени. «Не пришло
сообщение»: участник → рассылка → строки «Доставка рассылки» → номер попытки и
ответ мессенджера, затем строки журнала с этим `delivery_id`. «Бот не понял
нажатие»: журнал по `callback_id` — принято или отброшено как повтор, какой
обработчик выбран, на каком шаге остался диалог.

**Метрики.** Отдаются на `127.0.0.1` в формате Prometheus, наружу не
публикуются:

1. `/healthz` — бэкенд отвечает и видит PostgreSQL. Его ждёт деплой
   (`deploy/deploy.sh`) и проверка публичного адреса.
2. `/metrics` — счётчики событий по каналу и результату; отправки по статусу и
   коду ошибки; длительность обработки события и запросов API (гистограмма);
   глубина очереди доставки и возраст самой старой строки «в очереди»;
   прохождения по статусам; рассылки по статусам.

Порог тревоги по очереди — не глубина, а возраст строки «в очереди»: медленная
отправка при тысяче получателей нормальна, а строка, застрявшая на час, — сбой
воркера.

**Результаты рассылок и опросов.** Видны без журналов: в карточке рассылки —
получателей, доставлено, ошибок, статус, причина отмены; на вкладке «Доставка» —
строка на каждую пару «участник + канал» с номером попытки и ответом
мессенджера; в «Контроле» — список «Ошибки доставки»; по опросам — выгрузка в
Excel. Тестовая рассылка в статистику обычной не попадает.

**Проверки после деплоя.** Деплой ждёт `/healthz`, затем проверяет публичный
`https://kmi9site.ru/healthz`; после этого — один проход сценария на локальном
стенде (Телеграм — long polling) и проверка, что воркер забрал тестовую строку
очереди. Ошибка любого шага — повод откатиться на предыдущий образ.

## Сборка, тесты, деплой

**GitHub:** `git@github.com:kmi9work/community.git`. Сервер — `45.133.210.22`,
публичный адрес — `https://kmi9site.ru`.

**CI/CD** (`.github/workflows/deploy.yml`, на каждый push в `master` и по кнопке
«Run workflow»):

1. GitHub Actions подключается к серверу по SSH ключом из секрета
   `DEPLOY_SSH_KEY`;
2. на сервере: `git fetch --prune origin && git reset --hard origin/master` в
   `/opt/community`;
3. `deploy/deploy.sh`: бэкап базы → обновление образов → `up -d` → ожидание
   `/healthz` → проверка публичного `https://kmi9site.ru/healthz`.

Деплои не идут параллельно: второй ждёт первого. Первичная установка на новом
сервере — `deploy/bootstrap.sh`. Бэкап базы делается перед каждым обновлением в
`deploy/backups/`, хранятся 7 последних; восстановление и откат — в
`deploy/README.md`.

**Проверки перед деплоем.** Сценарии бота на локальном стенде: Телеграм —
long polling, MAX — long polling только для разработки (при активном webhook он не
работает). Миграции базы применяются один раз при деплое, воркер рассылки их не
запускает.

## Открытые вопросы

1. Канал доставки сообщений «Написать организатору»: пересылка в чат организаторов,
   запись в CRM или почта — в описании не задан.
2. Поведение при заполнении лимита мест: отказ в записи, лист ожидания или
   переполнение — в описании не задано.
3. Отмена записи самим участником: сейчас только через организатора, кнопки в боте
   нет.
4. Число автоматических попыток доставки до перехода строки в «ошибка».
5. Срок хранения журналов и метрик: ротация по размеру срок не задаёт, отдельного
   хранилища нет. Нужен ли срок (например, 14 дней) и кто, кроме администратора
   сервера, читает журналы.
6. Оповещение о сбоях: каким каналом (почта, Телеграм) и при каких порогах —
   недоступен `/healthz`, вырос возраст очереди, вырос поток 5xx. Сейчас тревогу
   подаёт только неудачный деплой.
7. Нужен ли администратору раздел со сводной статистикой (записи, прохождения,
   доставка по каналам за период): в описании его нет, результаты видны только в
   карточках и «Контроле».
