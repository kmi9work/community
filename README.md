# Техническое описание системы

Человеческое описание — `HUMAN_DESC.md` (источник истины: цели, сущности, шаги
пользователей, административный интерфейс, права). Здесь — как система устроена
технически: состав, модель данных, коды кнопок, алгоритмы, ограничения
мессенджеров, наблюдаемость и деплой. Код — в каталоге `system/`.

Человеческое описание относится к любому сообществу; специфика сообщества
«Кузница» — в `personal_docs/` (в git не хранится, на сервер копируется отдельно).

## Состав системы

| Часть | Технологии | Где в коде |
| --- | --- | --- |
| API админки и webhook ботов | Python 3.12, FastAPI, SQLAlchemy 2, Alembic | `system/backend/app/api/`, `app/main.py` |
| Бот (один на два мессенджера) | диспетчер сценариев, адаптеры Telegram Bot API и MAX Bot API (httpx) | `app/bot/`, `app/messengers/` |
| Воркер | очередь «Доставка рассылки», планировщик напоминаний, long polling для разработки | `app/worker.py`, `app/services/delivery.py` |
| CRM-админка | React 18 + TypeScript, Vite, PWA (manifest + service worker) | `system/frontend/` |
| База | PostgreSQL 16 (в тестах — также SQLite) | `app/models.py`, `migrations/` |
| Публичный фронт | nginx на сервере, TLS Let's Encrypt, `kmi9site.ru` | `system/deploy/nginx/` |

Участники в CRM не заходят: всё, что им доступно, — сообщения и кнопки бота.
Учётные записи есть только у администраторов; ролей внутри CRM нет.

## Архитектура

```
Телеграм ─ webhook /webhook/telegram ─┐
MAX ────── webhook /webhook/max ──────┴→ адаптер → Incoming → диспетчер → сценарий
                                                           │          (DialogState в БД)
                                                           ↓
                                                      PostgreSQL ← API ← админка (React PWA)
                                                           ↑
                     воркер: очередь доставки → адаптер → Телеграм / MAX
                     планировщик: напоминания → рассылка → очередь
```

**Один бэкенд, два мессенджера.** Адаптер (`messengers/telegram.py`,
`messengers/max.py`) приводит входящее событие к одному виду `Incoming` (старт,
текст, нажатие, контакт, отписка) и умеет три исходящие операции: отправить
сообщение (текст или афиша с подписью), отредактировать сообщение, ответить на
нажатие. Сценарии не знают, какой мессенджер перед ними. Различия:

| | Телеграм | MAX |
| --- | --- | --- |
| Меню участника | постоянная клавиатура (reply keyboard) | inline-кнопки `menu:*` под сообщением и команды `/start`, `/menu` |
| Запрос телефона | кнопка `request_contact` клавиатуры | inline-кнопка `request_contact`, номер из `vcf_info` |
| Отписка от бота | `my_chat_member` со статусом `kicked` | `bot_stopped`, `dialog_removed` |
| Отсечка повторов | `update_id` | `mid` сообщения, `callback_id`, `timestamp` |
| Разметка | HTML | HTML (`format: html`) |
| Афиша | `sendPhoto`, `file_id` кешируется в мероприятии | загрузка `POST /uploads`, `token` кешируется |
| Webhook-секрет | `X-Telegram-Bot-Api-Secret-Token` | `X-Max-Bot-Api-Secret` |

**Состояние — в базе.** Шаг диалога (`DialogState`), прохождение формы
(`SurveyRun`), очередь доставки (`Delivery`) лежат в PostgreSQL. Перезапуск и деплой
не теряют начатый диалог. Обработка события идёт в одной транзакции с блокировкой
строки `DialogState` (`SELECT … FOR UPDATE`), поэтому два быстрых нажатия одного
человека обрабатываются по очереди; сбой обработчика откатывает его изменения
(savepoint), участник получает `90-error-retry`.

**Входящее событие.** Webhook проверяет секрет, адаптер разбирает событие, диспетчер
пишет ключ события в `InboundEvent` (уникальный ключ — повтор отбрасывается),
выбирает обработчик: регистрация (участника нет) или меню зарегистрированного.
Мессенджеру всегда отвечаем 200 — иначе он повторит событие.

**Исходящие сообщения.** Ответы на действия участника отправляются сразу (один
повтор при сетевой ошибке, пауза из `retry_after`). Рассылки — только через очередь
воркера.

## Модель данных

Полный перечень полей с признаком обязательности — в `HUMAN_DESC.md`, раздел
«Сущности в CRM». Таблицы (`app/models.py`):

| Объект | Таблица | Ключевые правила |
| --- | --- | --- |
| Участник | `participants` | `telegram_id`, `max_id` уникальны; телефоны — нет |
| Документ о согласии | `consent_documents` | «Действует» — одна редакция (остальные снимаются при сохранении) |
| Согласие | `consents` | новая редакция или повторное согласие — новая запись |
| Уровень участия | `levels` + `level_event_types`, `level_activity_types` | `identifier` не меняется |
| Тип деятельности | `activity_types` | `identifier` = `<уровень>_<номер>` при наполнении |
| Тип мероприятия | `event_types` | `level_id` — базовый уровень (где тип появляется впервые) |
| Мероприятие | `events` | статус: `planned` / `moved` / `cancelled` / `completed` |
| Участие в мероприятии | `participations` | одна запись на пару «участник + мероприятие» |
| Участие организатора | `organizer_participations` + `organizer_participation_roles` | ролей несколько, только вида «организатор» |
| Роль на игре | `game_roles` | вид: участник / организатор; «Активна» |
| Подписка на тип мероприятия | `subscriptions` | одна запись на пару «участник + тип» |
| Интерес участника | `interests` | участник + уровень + тип деятельности |
| Опросник | `questionnaires` | анкета записи — одна |
| Вопрос | `questions` + `question_event_types` | «Типы мероприятий» пусто — для всех типов |
| Вариант ответа | `answer_options` | |
| Прохождение опроса | `survey_runs` | статус: `started` / `completed` / `declined` |
| Ответ | `answers` + `answer_selected_options` | одна строка — один ответ; повтор — новая строка |
| Отказ от опроса | `survey_refusals` | пустой опросник — отказ от всех |
| Напоминание | `reminders` | `hours_before`, `sent_at` |
| Рассылка | `broadcasts` + `broadcast_event_types`, `broadcast_levels`, `broadcast_participants` | автор пусто — система |
| Доставка рассылки | `deliveries` | уникальна тройка «рассылка + участник + канал» |
| Обращение | `appeals` | только в CRM |

Значения перечислений хранятся латиницей (`registered`, `came`, …), подписи — в
словарях `models.py` и метаданных API.

**Служебные поля и таблицы** (нужны реализации, человеку не видны):

1. `participants.telegram_active`, `max_active` — бот не заблокирован в этом
   мессенджере. Отписка в одном мессенджере снимает признак, рассылки туда не идут.
2. `events.poster_telegram_file_id`, `poster_max_token` — кеш загруженной афиши.
3. `survey_runs.question_ids` (вопросы прохождения фиксируются при старте — «Вопрос
   n из m» не прыгает), `message_id` (сообщение с текущим вопросом), `pending`
   (отметки «выбора нескольких» до «Готово»).
4. `broadcasts.payload` — данные системной рассылки (прежние дата и время, причина).
5. `deliveries.next_attempt_at` — когда повторить строку (пауза «слишком часто» или
   повтор после сетевой ошибки).
6. `admins` — учётные записи администраторов; `participant_id` — своя карточка
   участника для «Отправить себе».
7. `dialog_states` — шаг диалога и черновик регистрации до согласия.
8. `inbound_events` — ключи входящих событий (хранятся 7 дней).
9. `saved_views` — представления списков; системные создаются при наполнении.
10. `audit_log` — кто и когда изменил данные (администратор, участник, система).

**Правила.**

1. `identifier` после создания не меняется (API отвечает 422).
2. Справочные записи не удаляются: роль и тип выводятся «Активна = нет».
3. Роль на мероприятии — ссылка на справочник: переименование меняет название везде.
4. Один человек — одна карточка: второй мессенджер привязывается к найденной по
   телефону мессенджера карточке после ответа «Это я». Совпадение контактных
   телефонов карточки не склеивает.
5. **Удаление.** Когда у участника не остаётся ни одного активного мессенджера
   (отписка в обоих, или в единственном, которым он пользовался), карточка
   переводится в «удалён»: имя, фамилия, телефоны, идентификаторы мессенджеров
   стираются, тексты обращений очищаются, шаг диалога удаляется; дата удаления,
   записи на мероприятия, согласия и ответы остаются обезличенными.

## Начальное наполнение (`app/seed.py`)

Выполняется при каждом старте `api` и ничего не дублирует — каждая группа данных
создаётся, только если её ещё нет:

1. `personal_docs/levels.md` → уровни (`**new. Название**`), типы мероприятий
   (строка «Типы мероприятий: …») и типы деятельности (`- 1.1. …`). Базовый уровень
   типа — первый уровень, где тип упомянут. Identifier типа: «Игры» → `game`,
   «Лекции» → `lecture`, «Деловые игры» → `business_game`, «Клуб Кейсы» →
   `cases_club`, «Рефлексивный семинар» → `seminar`, остальные — транслитерацией.
2. Роли на игре — из `HUMAN_DESC.md`.
3. `personal_docs/law.md` → действующая редакция «Документа о согласии».
4. `personal_docs/questions/<identifier типа>.md` → вопросы анкеты записи с
   этим типом в поле «Типы мероприятий». Разбор: строка — вопрос; `- …` — вариант;
   `*` в начале — «Спрашивать при каждой записи»; «(выбор одного варианта)» —
   выбор одного; «(возможность выбрать до N вариантов)» — выбор нескольких с
   максимумом N; «(Поле для ввода текста)» — открытый. Вопросы с выбором —
   обязательные, открытые — нет.
5. Системные представления (раздел «Контроль»).
6. Первый администратор из `ADMIN_LOGIN` / `ADMIN_PASSWORD`, если учётных записей нет.

## Регистрация участника (Шаг 0)

Шаги (`bot/registration.py`): `new` → `reg_name_confirm` | `reg_name_input` →
`reg_phone` → [`reg_known_card`] → `reg_contact_offer` → [`reg_contact_input`] →
`reg_consent` → `idle`. До согласия карточки нет: черновик — в `DialogState.data`.
Повторный `/start` повторяет текущий шаг.

1. Приветствие `01`, затем имя: если в профиле есть имя и фамилия — `02` с
   «Да» (`reg:name_yes`) / «Ввести заново» (`reg:name_no`), иначе просьба написать
   имя и фамилию одним сообщением (без фамилии — просим снова).
2. Телефон мессенджера `03` с кнопкой запроса контакта. Номер руками не принимается:
   первый раз — `04`, дальше бот повторяет `03`. Чужой контакт не принимается.
3. Номер приводится к виду `+7…`. Если он совпал с телефоном мессенджера активной
   карточки из другого мессенджера — `05` с «Это я» (`reg:card_yes`) / «Нет, я
   новый» (`reg:card_no`).
4. Контактный телефон `06`: «Да» (`reg:contact_yes`) или «Другой номер»
   (`reg:contact_no`) → `07` с «Отмена» (`reg:contact_back`); текст без номера —
   `08` и пример.
5. Согласие `09` со ссылкой действующей редакции: «Согласен» (`reg:consent_yes`) —
   карточка создаётся (или к найденной привязывается мессенджер), пишется
   «Согласие» (редакция, канал, время), ставятся подписки на типы уровня `new`,
   `11` с меню. «Не согласен» (`reg:consent_no`) — `10`, черновик стирается.
6. Если администратор отозвал согласие, бот перед любым действием снова просит
   согласие (`09`); новое согласие — новая запись.

Меню участника: «Мероприятия», «О сообществе», «Мои данные», «Написать
организатору». Непонятный текст — `12` с меню.

## Сценарий №1. Запись на мероприятие

1. «Мероприятия» → `20`: типы (`ev:type:<identifier>`, активные, по порядку) и
   «Все» (`ev:all`). Предстоящие: статус «запланировано» или «перенесено», дата не
   раньше сегодняшней; до 20 штук по дате и времени. Каждое — анонс с кнопкой
   «Записаться». Пусто — `21`.
2. Анонс (`22`): афиша с подписью «название / дата, время / адрес», без времени —
   без запятой, без адреса — без строки. Описание — абзацем, если подпись остаётся
   в лимите (1024 в Телеграм, 4000 в MAX), иначе отдельным сообщением `23` (длинное
   — частями с пометкой «продолжение»). В рассылке — ещё «Отписаться: (тип)»
   (`ev:unsub:<type_id>`; длиннее 20 символов — «Отписаться», тип в подписи).
3. «Записаться» (`ev:join:<event_id>`):
   - мероприятие прошло, отменено или проведено — `32`;
   - запись «записан» уже есть — `25`;
   - «Лимит мест» заполнен (записанных со статусом «записан» столько же) — `31`;
   - начатое прохождение анкеты по этому мероприятию — продолжается с текущего
     вопроса;
   - вопросы анкеты: активные, по порядку, с пустыми «Типами мероприятий» или с
     типом мероприятия; без звёздочки — только если участник ещё ни разу не
     отвечал на этот вопрос (в любом опроснике и мероприятии);
   - вопросов нет — сразу запись и `24`, иначе форма.
4. Завершение формы — снова проверка открытости и лимита мест, затем «Участие»
   «записан» (отменённая раньше запись возвращается в «записан»), `24`.
5. «Отписаться» — «Подписан = нет», дата изменения, `26`.
6. Диплинк `?start=ev<id>` открывает запись на мероприятие.

## Форма в боте (`bot/form.py`)

Общая логика — `docs/form/README.md`; здесь — как сделано.

1. Сообщение вопроса — `27` («Вопрос n из m» и текст). Для открытого — добавляется
   `29`; для «выбора нескольких» — строка «Можно выбрать до N. Выбрано: k.».
2. Варианты — кнопка на строку. Текст кнопки — до 20 символов; если хоть один
   вариант длиннее, варианты нумеруются и полностью перечисляются в тексте
   сообщения, полный текст нажатого варианта приходит всплывающим уведомлением.
3. Ответ сохраняется строкой «Ответ», сообщение вопроса правится: клавиатура
   снимается, внизу — «Ответ: …»; следующий вопрос — новым сообщением. Отметки
   «выбора нескольких» правят то же сообщение.
4. Лимит «Максимум выбранных вариантов» проверяет бот: лишний вариант не
   ставится, отдельным сообщением — `28`. Обязательный вопрос без отметок —
   уведомление «Выберите хотя бы один вариант».
5. «Пропустить» есть только у необязательного вопроса; ответ не пишется.
6. Открытый ответ — только текст; нажатие кнопки варианта в этот момент — подсказка
   `29`; текст длиннее 4096 (Телеграм) / 4000 (MAX) не обрезается — `91`.
7. Кнопка относится к прохождению, а не к шагу диалога: нажатие на уже отвеченный
   вопрос даёт уведомление «Этот вопрос уже позади» и второго ответа не создаёт;
   бит в `m:` — желаемое состояние, двойное нажатие не переключает обратно.
8. Нажатие кнопки меню во время формы не теряет прохождение: оно остаётся «начат»,
   `/start` или повторное «Записаться» продолжает с текущего вопроса.
9. «Отказаться» (`x:<прохождение>`) — статус «отказ», запись в «Отказ от опроса»,
   `30` (анкета записи) или `41` (опрос); запись на мероприятие не создаётся.
10. Правка сообщения старше 48 часов в Телеграм невозможна — тогда вопрос
    отправляется новым сообщением.

Коды кнопок формы:

```
q:<вопрос>:<вариант>          выбор одного варианта
m:<вопрос>:<вариант>:<бит>    переключатель «выбора нескольких» (бит 1 — отметить, 0 — снять)
g:<вопрос>                    «Готово»
s:<вопрос>                    «Пропустить»
x:<прохождение>               «Отказаться»
```

## Сценарий №2. Опрос

1. В карточке опросника «Разослать опрос» создаёт черновик рассылки вида «опрос»
   (по умолчанию — по уровням) и открывает его карточку: получатели, предпросмотр,
   «Отправить себе», «Отправить».
2. «Подписан на уровень» — участник выбрал уровень в интересах или подписан хотя
   бы на один тип мероприятия, базовый уровень которого — этот уровень. Поэтому
   новый участник (подписки уровня `new`) попадает в рассылку по уровню `new`.
3. Исключаются: отказ от всех опросов, отказ от этого опросника, удалённые, без
   согласия, без активного мессенджера.
4. Приглашение `40`: «Пройти опрос» (`sv:take:<id>`), «Отказаться»
   (`sv:decline:<id>`), «Отказаться от всех» (`sv:decline_all`).
5. «Пройти» — форма по тем же правилам (без звёздочки — только неотвеченные). Все
   вопросы уже отвечены — сразу `43`, прохождение пишется завершённым.
6. «Отказаться» — `41`; «Отказаться от всех» — флаг в карточке и отказ без
   опросника, `42`. Администратор снимает отказ, удалив строку на вкладке «Отказы».

## Сценарий №3. О сообществе и интересы

1. «О сообществе» → `50`: текст `personal_docs/description.md` и уровни с типами
   деятельности из CRM. Не помещается — описание и уровни отдельными сообщениями.
2. «Выбрать интересы» (`int:start`) → `52`: уровни с пронумерованными типами
   деятельности. «Уровень N» (`int:level:<id>`) отмечает или снимает весь уровень,
   номер (`int:activity:<id>:<уровень>`) — один тип; сообщение правится.
3. «Сохранить» (`int:save`): снятые интересы удаляются, новые пишутся с датой;
   по уровням, выбранным впервые, ставится «Подписан = да» на все активные типы
   мероприятий уровня. Снятие интереса подписку не меняет. `51` (пустой выбор —
   «Выбор пуст — подписки не изменились»).

`60` с кнопками; переходы по кнопкам правят то же сообщение.

## Сценарии №5 и №6. Напоминания, перенос, отмена

1. Планировщик (воркер, раз в 30 секунд) берёт активные неотправленные напоминания
   запланированных и перенесённых мероприятий. Начало мероприятия — дата и время в
   часовом поясе сообщества (`TIMEZONE`, без времени — начало дня). Срок наступил и
   мероприятие ещё не началось → системная рассылка «напоминание» записавшимся
   («записан»), в напоминании — время отправки.
2. Текст — `70`; свой текст напоминания заменяет шаблон, подстановки те же.
3. **Перенос** («Перенести»: новые дата, время, адрес и обязательная причина):
   прежние дата и время — в «Прежнюю дату и время», статус «перенесено», причина,
   неотправленные рассылки-напоминания отменяются, у напоминаний сбрасывается
   «Отправлено» (срок считается от новой даты), записавшимся — `80`.
4. **Отмена** (обязательная причина): статус «отменено», напоминания не уходят,
   записавшимся — `81`.
5. **Проведение**: статус «проведено», неотправленные напоминания отменяются.
6. Пока на мероприятие никто не записан, дату, время и адрес можно поправить прямо
   в карточке; после первой записи — только кнопкой «Перенести».

## Рассылки и доставка

Статусы рассылки: `draft` → `queued` → `sending` → `finished`; `cancelled` — из
черновика или во время отправки. Править можно только черновик.

1. **Запуск.** Получатели отбираются способом выбора, на каждую пару «участник +
   активный канал» создаётся строка доставки «в очереди», попытка 1; в рассылку —
   число получателей.
2. **Отправка.** Воркер берёт строки пачками (`FOR UPDATE SKIP LOCKED`), каждая —
   своя транзакция; содержимое собирается в момент отправки; между сообщениями —
   пауза `SEND_PAUSE_SECONDS` (0,05 с). После каждой строки пересчитываются
   «Доставлено» и «Ошибок»; очередь пуста — рассылка «завершена».
3. **Ошибки.** «Слишком часто» — строка ждёт время из ответа, попытка не
   расходуется. Сетевые ошибки и 5xx — повтор через 10, 20 с…, до
   `MAX_SEND_ATTEMPTS` (3) попыток, затем «ошибка». 400/404 — сразу «ошибка».
   Пользователь заблокировал бота — «ошибка», канал помечается неактивным (если
   других нет — карточка удаляется).
4. **«Повторить ошибки»** возвращает строки «ошибка» в очередь с номером попытки +1.
5. **Отмена** останавливает неотправленные строки; доставленное не отзывается.
6. **«Отправить себе»** создаёт отдельную тестовую рассылку (`is_test`) только на
   карточку участника администратора; статистика исходной рассылки не меняется.
7. **Системные рассылки** (напоминание, изменение мероприятия) — автор «система»,
   способ выбора «записанные на мероприятие», та же очередь.

Способы выбора получателей: все активные; по типам мероприятий (подписан на любой
из типов); по уровням (см. сценарий №2); выбранные участники; записанные на
мероприятие. Всегда исключаются удалённые, без согласия и без активного
мессенджера; для опроса — отказавшиеся.

Текст администратора (рассылка «текст», свой текст напоминания, текст вместо
описания в опросе и анонсе) — HTML с разрешёнными `<b>`, `<i>`, `<u>`, `<s>`,
`<code>`, `<pre>`, `<a href="https://…">`; остальное экранируется. В рассылке
«текст» тема — жирным заголовком.

## Административный интерфейс

Адрес — `https://kmi9site.ru`. React-приложение (PWA: устанавливается на телефон,
оболочка кешируется service worker, данные и афиши — никогда), API — `/api/…`.

**Вход.** Логин и пароль (scrypt), cookie-сессия `crm_session` (подписана, HttpOnly,
Secure, SameSite=Lax, 7 дней); смена пароля завершает прочие сессии. Не больше 10
неудачных входов за 15 минут с одного адреса. Изменяющие запросы принимаются только
с заголовком `X-Requested-With: fetch` (защита от CSRF).

**Разделы.** Участники, Мероприятия, Опросы, Рассылки, Обращения; Справочники
(типы мероприятий, уровни, типы деятельности, роли, документы о согласии); Контроль;
Администраторы; Профиль.

Число необработанных обращений рядом с пунктом «Обращения» — `GET /api/counters`
(`appeals_unread`); обновляется при переходе по разделам и раз в 30 с.

**Списки** (общий компонент `DataTable`, общий API `/api/r/<раздел>`): поиск,
сортировка по колонке, выбор колонок (запоминается в браузере), inline-правка
ячейки (щелчок; первая колонка открывает карточку), пагинация по 50. Фильтры
убраны под кнопку «Фильтры»: панель открывается по нажатию, показывает число
активных фильтров и закрывается по клику вне неё. Набор поиска, фильтров,
сортировки и колонок сохраняется как представление (`saved_views`). Параметры
списка — в адресе страницы, поэтому ссылкой можно поделиться.

В списке участников доступны колонки «Подписки» (типы мероприятий с
«Подписан = да»), «Уровни» и «Типы деятельности»; «Уровни» учитывают и подписки —
уровень типа, на который участник подписан, показывается наравне с уровнем из
«Интересов» (так же считает отбор получателей «по уровням»).

| Раздел | Карточка: вкладки и действия |
| --- | --- |
| Мероприятия | Основное (поля, афиша, «Разослать анонс», «Перенести», «Отменить», «Провести», «Список для мастера»), Участники («Добавить», «Отметить всех пришедшими», «Снять отметки», роль/статус/присутствие в списке), Организаторы, Напоминания, Рассылки, Ответы («Выгрузить в Excel») |
| Участники | Данные («Отозвать согласие»), Согласия, Подписки, Интересы, Записи, Опросы, Отказы, Обращения |
| Опросы | Основное («Разослать опрос»), Вопросы, Прохождения («Выгрузить в Excel»), Отказы; карточка вопроса — варианты ответа; карточка прохождения — ответы |
| Рассылки | Рассылка (поля черновика, предпросмотр сообщения, число и список получателей, «Отправить себе», «Отправить», «Отменить рассылку», «Повторить ошибки», прогресс), Доставка |
| Обращения | текст, канал, дата; «Обработано» и комментарий |

**Афиша.** Загрузка в карточке мероприятия: JPEG или PNG, до 5 МБ, размер в
пикселях любой (рекомендуемый — 1080 × 1350); иначе файл не сохраняется и причина
показывается. Файл — `(identifier типа)-(дата)-(id).jpg` в томе `media`; отдаётся
только вошедшему администратору. Бот отправляет файл как есть.

**Список для мастера** — печатная HTML-страница: название, дата, время, адрес,
записанные со статусом «записан» (имя, контактный телефон, роль, последние ответы
на вопросы со звёздочкой по этому мероприятию, пустая колонка «Явка»). Открытие
пишется в журнал аудита.

**Контроль** — системные представления: «Предстоящие игры», «Ошибки доставки»,
«Брошенные прохождения», «Отменили запись», «Отписались», «Необработанные обращения».

## Выгрузка ответов в Excel

`GET /api/export/runs` с фильтрами списка прохождений (по умолчанию — завершённые).
Лист «Прохождения»: строка — прохождение (участник, телефон, опросник, мероприятие,
дата, статус, канал, начат, завершён), столбцы — вопросы опросников из выборки; для
вопроса со звёздочкой — последний ответ, для «выбора нескольких» — варианты через
«; ». Лист «Ответы» — все ответы строками. Все строковые ячейки записываются как
текст (значения на `=`, `+`, `-`, `@` формулой не станут). Имя файла —
`(identifier опросника)-(дата).xlsx`. Больше `EXPORT_ROW_LIMIT` (20 000) прохождений —
ответ 413 с просьбой сузить фильтр.

## Тексты сообщений

Источник — `personal_docs/messages/`, одно сообщение — один файл, текст — блоки
` ```text `. Бот обращается к шаблону по номеру файла (`render("22")`); второй блок
файла — вариант сообщения (`02`, `21`, `27`, `66`, `67`). Подстановки `{{имя}}`
экранируются; пустое значение убирает «, {{имя}}» или всю строку, пустых строк
больше одной не остаётся. Тексты читаются при старте процесса. Тест
`test_real_templates_have_expected_keys` сверяет набор шаблонов и подстановок с
тестовыми шаблонами (`tests/fixtures/personal_docs/messages`).

## Безопасность и персональные данные

1. Доступ к CRM — только администраторам; публичной регистрации нет.
2. Наружу — только HTTPS через nginx; приложение слушает `127.0.0.1:3100`.
3. Секреты (пароль базы, ключ сессии, пароль первого администратора, секреты
   webhook) генерируются на сервере в `system/deploy/.env` (права 600), в git не
   попадают. Токены ботов вписываются туда же.
4. Webhook принимается только с секретом, заданным при регистрации webhook.
5. Персональные данные, ответы, выгрузки и афиши доступны только вошедшему
   администратору; ответы API и выгрузки не кешируются; service worker не кеширует
   данные.
6. Согласие — запись на конкретную редакцию; отзыв — отдельное действие, прежние
   записи не переписываются; без действующего согласия участник не получает
   рассылок, а бот снова просит согласие.
7. Удаление при отписке — см. «Модель данных», правило 5.
8. Выгрузка в Excel пишет значения текстом.
9. Ошибки участнику — без технических подробностей (`90`), детали — в журнал.
10. Каждое изменение данных администратором, рассылка, изменение мероприятия,
    открытие списка для мастера и выгрузка пишутся в `audit_log` (кто, когда, что).

## Наблюдаемость

1. **Записи CRM** — основной источник фактов: статус записи и прохождения, строка
   доставки с номером попытки и ответом мессенджера, `audit_log`.
2. **Журналы** — stdout контейнеров, одна строка — одно событие в JSON (`ts` UTC,
   `level`, `service` = `api` / `worker` / `cli`, `event`, идентификаторы). Ротация
   docker: 10 МБ × 5 файлов на сервис. В журнал не пишутся тексты ответов,
   телефоны, адреса, токены и пароли — только идентификаторы и коды.
   Основные события: `inbound.handled` (канал, тип, код кнопки, шаг до и после,
   длительность), `inbound.duplicate`, `bot.sent` / `bot.send_failed`, `form.*`,
   `participant.*`, `broadcast.launched` / `finished` / `cancelled` / `retry`,
   `delivery.sent` / `error` / `rate_limited` / `retry_scheduled`,
   `scheduler.tick` (созданные напоминания, глубина и возраст очереди),
   `admin.login` (результат, без пароля), `admin.created` / `updated` / `deleted`,
   `admin.export`, `http.request` (метод, шаблон пути, код, длительность — без тела).
3. **Метрики** — `/metrics` (Prometheus) только с самого сервера
   (`curl 127.0.0.1:3100/metrics`; nginx отдаёт 404): `bot_inbound_events_total`
   (канал, результат), `bot_sends_total` (канал, статус), `bot_handle_seconds`,
   `http_request_seconds` (метод, путь, код), `delivery_queue_depth`,
   `delivery_queue_oldest_seconds`, `survey_runs_by_status`, `broadcasts_by_status`,
   `deliveries_by_status`. Счётчики — на процесс `api` (у uvicorn два процесса —
   значения по одному из них), показатели из базы — общие. Тревожный признак —
   возраст самой старой строки очереди, а не глубина.
4. **`/healthz`** — база отвечает; в ответе — загружены ли тексты и заданы ли
   токены ботов. Его ждёт деплой.

Разбор жалобы — от идентификатора: «не пришло сообщение» — участник → рассылка →
строки доставки (попытка, ответ мессенджера) → журнал по `delivery_id`; «бот не
понял нажатие» — журнал `inbound.handled` по коду кнопки и участнику.
