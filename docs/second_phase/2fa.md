# Второй фактор входа администратора

Статус: следующая очередь. В текущей версии CRM вход — по логину и паролю без
второго фактора; описание ниже в README не входит и реализуется отдельной
задачей.

## Зачем

`HUMAN_DESC.md` (раздел «Административный интерфейс») требует вход «по логину и
паролю с двухфакторной аутентификацией». В README вход описан без второго
фактора; расхождение снимается, когда задача будет выполнена. Доступ к CRM есть
только у администраторов, и в их руках персональные данные участников, ответы и
выгрузки — второй фактор закрывает самый дорогой риск: украденный пароль.

## Требования

1. Второй фактор — одноразовый код TOTP в Яндекс.ID. Приложение-аутентификатор
   выдаёт шестизначный код, срок действия и окно проверки — стандартные для TOTP
   (30 секунд).
2. Порядок входа: логин → пароль → код TOTP. Без верного кода сессия не
   создаётся; промежуточное состояние «пароль верен» не даёт доступа к данным.
3. Второй фактор обязателен для всех учётных записей администраторов. Участники
   в CRM не заходят, поэтому у них второго фактора нет.
4. Привязка фактора — к учётной записи администратора в CRM, а не к устройству:
   администратор может пользоваться другим телефоном с тем же TOTP-секретом.
5. Код проверяется на сервере. Ответ на неверный код не должен подсказывать,
   существует ли учётная запись.
6. Вход и ошибки входа пишутся в лог: учётная запись, время, результат, адрес
   клиента. Код TOTP в лог не попадает.
7. Второй фактор не заменяет HTTPS и не отменяет требование хранить секреты
   только на сервере (`deploy/.env`, права 600).

## Открытые вопросы

До реализации нужно решение по каждому пункту — в описании их нет.

1. Восстановление доступа при потере фактора: резервные коды, сброс другим
   администратором или обращение к владельцу сервера.
2. Сколько неверных кодов допускается и на сколько блокируется вход после
   исчерпания попыток.
3. Что делать с уже открытыми сессиями в момент включения второго фактора:
   завершить все или дать дожить.
4. Нужен ли второй фактор при смене пароля и при выдаче новой учётной записи.
5. Резервный канал входа на случай недоступности Яндекс.ID: есть ли он и кто им
   пользуется.

## Что поправить при реализации

1. `README.md`, раздел «Состав системы», пункт про CRM и админку: вернуть второй
   фактор в описание входа.
2. `README.md`, раздел «Административный интерфейс»: порядок входа с кодом TOTP.
3. `README.md`, раздел «Безопасность и персональные данные», пункт 1: второй
   фактор, лог входов, отсутствие кода в логах.

   администратора и журнал входов.
